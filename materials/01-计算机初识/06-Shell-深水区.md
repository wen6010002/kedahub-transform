## 先把东西装上

**Windows 用户先装 Git Bash。** 这一站的命令在 Windows 自带的命令提示符和 PowerShell 里跑不了。

1. 打开浏览器搜「git 下载」，第一个就是官网
2. 下载 Windows 版，双击安装，一路点「Next」用默认选项。问你默认编辑器选什么的时候别选 Vim，新手不知道怎么退出来
3. 装完在开始菜单里搜 `Git Bash` 打开

装好之后敲 `pwd`。Windows 上显示 `/c/Users/你的名字`，Mac 上显示 `/Users/你的名字`，看到路径就对了。

## 这一份讲的是什么

引路版讲的是你每天都要用的东西。这一份讲的是你偶尔会撞上、撞上了会很头疼的东西。

它们的共同点是：Shell 在你没注意的时候做了很多决定，而这些决定偶尔会和你的预期不一样。你以为 `$f` 就是一个文件名，其实 Shell 会先把它拆成好几段再交出去。你以为循环里改的变量就是改了，其实那是在另一个进程里改的。

下面每一条都对应一个具体的场景。如果你现在还没遇到过，读起来会觉得「这有什么好说的」，那就先放着，等撞上了再回来。之所以这么说，是因为这些内容脱离具体问题去看，真的记不住。

还有一条贯穿全篇的约定：下面的例子里变量名一律用英文。原因在第 7 站说过，Mac 自带的 bash 3.2 不认中文变量名，写了会报一个完全看不出原因的错。

## 引号有三层意思

这是 Bash 里一半诡异问题的源头。

同一个变量，加不加引号，行为完全不同。

**不加引号**的时候，Shell 会先做两件事：按空格把内容拆成好几段，再把里面的 `*` 之类当成通配符展开。假设有个变量存着 `我的 照片.png`：

```
name="我的 照片.png"
for x in $name; do echo "[$x]"; done
```

输出是两行：

```
[我的]
[照片.png]
```

接收方拿到的是两个东西。这就是为什么文件名里有空格时脚本会莫名其妙地失败。

**单引号**里面的一切原样保留，连变量都不展开：

```
echo '$name'    输出 $name
echo "$name"    输出 我的 照片.png
```

需要写「字面上的美元符号」时，单引号是唯一的选择。

**双引号**是你要的那个：变量会展开，但不拆词，也不展开通配符。

所以规则很简单，所有变量都用双引号包起来。加了不会有坏处，不加迟早出事。

还有一种写法是 `$'...'`，它额外支持 `\n` 这样的转义：

```
echo $'第一行\n第二行'
```

需要输出换行的时候用它，比 `echo -e` 更可靠。

## 循环里改的变量为什么会丢

这个坑几乎每个人都会踩一次：

```
count=0
cat 名单.txt | while read name; do
  count=$((count + 1))
done
echo $count
```

你期望它输出行数，实际输出 `0`。

原因是管道右边那个 `while` 跑在一个**子进程**里。子进程把 `count` 改成了 3，但它改的是自己的那一份，父进程完全不知道。Unix 从设计上就是这么定的，每个进程有自己独立的变量空间。

两种改法都能绕过去：

```
count=0
while read name; do
  count=$((count + 1))
done < 名单.txt
echo $count
```

用重定向代替管道，不产生子进程。

```
count=0
while read name; do
  count=$((count + 1))
done < <(cat 名单.txt)
echo $count
```

`<(...)` 叫进程替换，它把命令的输出做成一个临时文件再喂进来。看起来像管道，但不产生子进程。

顺便记住另一条相关的规则：**不加 `export` 的变量不会传给子进程。** 你在脚本里设了一个变量，然后调用另一个脚本，那个脚本是看不到它的，除非你 `export` 过。

## 什么时候该用 set -euo pipefail

在脚本开头加上这一行，能挡掉一大类事故：

```
set -euo pipefail
```

`-e` 是「任何命令失败就立刻退出」，`-u` 是「用了没定义过的变量就报错」，`-o pipefail` 是「管道里任何一环失败，整条算失败」。

为什么值得加？因为脚本最危险的时刻，是出错了却假装没事继续往下跑。举个例子，一个删文件的脚本，第一步取目录名失败了，如果没加 `-e`，它会拿着一个空变量继续执行第二步，然后你可能就删错了地方。

不过 `-e` 有几个例外，不知道的话会以为它没生效：

```
set -e
if false; then echo x; fi      # 不会退出
false || echo "接住了"          # 不会退出
false                          # 这一句会让脚本停下
```

放在 `if` 条件里的命令失败了不会退出，用 `||` 接过的命令失败了不会退出，`&&` 左半边的失败也不会退出。这些是故意留的口子，让你能写「这里允许失败」。

所以关键的那几步，最好还是显式写清楚：

```
cd "$DIR" || { echo "进不去 $DIR"; exit 1; }
```

## 变量还能这么玩

Bash 有一堆内置的字符串处理写法，学会之后能少调很多外部程序。

```
${var:-默认值}     没定义或者是空，就用默认值
${var:?提示语}     没定义就报错退出，提示语会打出来
${var#前缀}        从左边删掉最短的匹配
${var##前缀}       从左边删掉最长的匹配
${var%后缀}        从右边删掉最短的匹配
${var%%后缀}       从右边删掉最长的匹配
${var/旧/新}       替换第一处
${var//旧/新}      替换全部
${var:2:5}         从第 3 个字符起，取 5 个
```

最常用的是 `#` 和 `%` 这一对，因为它们能替代 `basename` 和 `dirname`：

```
f="报告_2024.pdf"
echo "${f%.*}"     输出 报告_2024
echo "${f##*.}"    输出 pdf
```

记法是这样的：`#` 在键盘上靠左，所以从左边删；`%` 在键盘上靠右，所以从右边删。单个符号是「最短匹配」，两个符号是「最长匹配」。

`${var:-默认值}` 在脚本里用得极多，尤其是配合 `set -u` 的时候：

```
echo "你好，${name:-同学}"
```

## 数组

```
files=(a.txt b.txt "有 空格的.txt")
echo "${files[0]}"      输出 a.txt，下标从 0 开始
echo "${#files[@]}"     输出 3，元素个数
```

遍历数组的时候有个细节要记住：

```
for x in "${files[@]}"; do
  echo "$x"
done
```

`[@]` 加引号，每个元素保持独立。如果写成 `${files[*]}` 或者漏掉引号，所有元素会被拼成一个字符串，带空格的文件名就散架了。

需要当字典用的时候有另一种数组：

```
declare -A score
score[小明]=90
echo "${score[小明]}"
```

注意 `declare -A` 是 bash 4 才有的功能。Mac 自带的 bash 是 3.2 版，跑不了这一段，要么装新版 bash，要么改用 zsh。数组元素的下标写中文是可以的，有坑的只是变量名。

## 通配符的几个细节

```
*        任意字符，但不跨目录
**       递归匹配所有层级，需要先 shopt -s globstar
?        单个字符
[abc]    括号里任意一个
[!abc]   括号里任意一个之外
{a,b,c}  花括号展开，生成多个参数
```

最后那个花括号和前面几个不是一类东西。通配符是「匹配已经存在的文件」，花括号是「凭空生成几个字符串」：

```
mkdir -p 项目/{前端,后端,文档}
```

这条命令会建三个目录。它跟当前目录里有什么东西完全无关。

有一个坑值得单独说。默认情况下，`*.txt` 如果没匹配到任何文件，Shell 会把 `*.txt` 原样传过去。于是你的脚本会收到一个字面量字符串 `*.txt`，然后尝试去处理一个叫这个名字的文件。

写循环处理文件的时候，开头加一行：

```
shopt -s nullglob
```

这样没匹配到就是空的，循环一次都不执行。

## 退出的时候记得收拾干净

脚本创建了临时文件，跑到一半被你按了 Ctrl 加 C，临时文件就留在系统里了。跑得多了会攒一堆。

`trap` 就是解决这个的：

```
tmp=$(mktemp)

cleanup() {
  rm -f "$tmp"
  echo "清理完了"
}

trap cleanup EXIT

echo "中间结果" > "$tmp"
```

`trap 函数名 EXIT` 的意思是「不管脚本怎么结束，正常结束也好、报错退出也好、被 Ctrl 加 C 打断也好，退出之前都先跑一遍这个函数」。

有一件事 `trap` 做不到：如果进程被 `kill -9` 强杀，它是抓不到的。这是操作系统层面的设计，`-9` 就是「不给任何机会」，接受它就行。

## 循环里别调外部程序

这条关系到脚本跑得动跑不动。

```
while read line; do
  echo "$line" | cut -d, -f2
done < 大文件.csv
```

一万行的文件，这段要跑好几分钟。因为每一轮都启动了一个新的 `cut` 进程，一万轮就是一万次进程创建。

同样的事换一个写法：

```
cut -d, -f2 大文件.csv
```

一秒不到。

Bash 自己的字符串操作（参数扩展、替换）比调外部程序快几个数量级。所以写循环之前先想一下：这件事能不能不循环就干完？

还有两个顺手的小技巧：读文件用 `$(< 文件名)` 比 `$(cat 文件名)` 快，因为省掉了启动 `cat` 那一步。要并行跑可以用 `xargs -P 8`。

## 动手任务

一、**亲手撞一次引号的墙。** 建一个叫 `有 空格.txt` 的文件，用 `for x in $name` 和 `for x in "$name"` 两种写法各遍历一次，看输出有什么不同。这个实验做一遍，比读十遍规则有用。

二、**修一个变量丢失的 bug。** 按上面的例子写一段用管道加 `while read` 的代码，在循环里累加一个计数，循环外打印，看它是不是 0。然后改成重定向写法，再跑一次。

三、**给上一站的整理脚本加上 `set -euo pipefail`。** 加上之后故意让脚本中间失败一次，比如把 `DIR` 改成一个不存在的目录，观察它是不是立刻停下。

四、**用参数扩展替换一次外部命令。** 找一段用了 `basename` 或 `sed` 拿文件名的代码，改成 `${f%.*}` 的写法。

五、**加一个 `trap`。** 让脚本创建临时文件，用 `trap` 保证退出时删掉。跑一半按 Ctrl 加 C，确认临时文件没留下。

六、**跑一次 ShellCheck。** 把前几站写的所有脚本都扫一遍，看它报什么。不用全改，但要能说出它为什么这么报。

## 正式产出

**一个别人拿去就能用的脚本。**

选题自定，但要满足几条：开头有 `set -euo pipefail`；每一步失败都有明确的提示，不是默默退出；用 `trap` 保证退出时清理干净；跑过 ShellCheck，没有 error 级别的报告；文件头部有注释，说清它干什么、怎么用、需要什么前提。

评判标准只有一条：把脚本发给一个不认识的同学，他不问你任何问题就能跑起来。做到这一点，说明你跨过了「自己能用」到「别人能用」那道坎。这两件事之间的距离，比看起来大得多。

## 卡住了看这里

**加了 `set -e`，脚本却在中途失败后继续跑。** `set -e` 有例外：放在 `if` 条件里的、用或运算接过的、与运算左半边的失败，都不触发。把关键命令改成显式判断，失败就 `echo` 一句再 `exit 1`。

**加了 `set -u` 之后，脚本动不动就退出。** 你在用可能没有的变量。改成 `${var:-}` 给个默认值，或者先显式判断一下。

**变量赋值那一行报「No such file or directory」。** 变量名用了中文。bash 3.2 不认，改成英文。

**Mac 上报 `declare -A` 语法错误。** Mac 自带 bash 是 3.2 版，太老。装新版 bash，或者直接用 zsh。

**`*.txt` 没匹配到文件，脚本却去处理了一个叫 `*.txt` 的东西。** 开头加 `shopt -s nullglob`。

**数组遍历时文件名带空格就散架。** 用了 `[*]` 或者漏了引号。改成 `"${files[@]}"`，两处引号都不能省。

**`trap` 里的清理没执行。** 脚本被 `kill -9` 强杀了，`trap` 抓不到。这是设计如此，改用可捕获的信号。

**zsh 里数组的第一个元素是空的。** zsh 的数组下标从 1 开始，不是 0。Mac 用户写脚本时，在开头明确写 `#!/bin/bash`，别依赖默认 Shell。

**脚本在终端里正常，放进定时任务就失败。** 定时任务几乎不加载任何环境变量。在脚本里用绝对路径，开头手动 source 需要的配置，或者显式 `export` 你要用的变量。
