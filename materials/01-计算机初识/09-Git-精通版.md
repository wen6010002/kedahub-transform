# Git · 精通版

计算机初识 · 第 9 站

时间：2 小时到 2 个半小时
做完你会有一个：一个公开的 GitHub 仓库，链接能发给同学

---

## 第一步：装上 Git

**Windows**

打开浏览器搜「git 下载」，第一个是官网。下载 Windows 版，双击安装。

安装过程会问你一堆问题，一路点「Next」用默认选项就行，不用改任何东西。只有一处可以注意：默认编辑器那一项，如果它让你选，选记事本或者 VS Code，别选 Vim，新手用 Vim 会不知道怎么退出。

装完之后，在开始菜单里搜 `Git Bash`，打开它。你会看到一个黑色的窗口。

**以后就用 Git Bash，不要用系统的「命令提示符」。** 因为网上几乎所有教程讲的都是 Linux 风格的命令，在 Git Bash 里能直接照做，在命令提示符里会报错。

另一个打开方式：在任意文件夹里点右键，菜单里有「Open Git Bash here」，会在那个文件夹里直接打开。

**Mac**

Mac 一般自带 Git。按 Command 加空格，输入「终端」，打开，敲：

```
git --version
```

如果显示版本号，说明有，跳到下一步。如果弹出一个小窗口让你安装「命令行开发者工具」，点安装，等它装完。

**验证装好了没有**

不管 Windows 还是 Mac，打开终端敲：

```
git --version
```

看到类似 `git version 2.43.0` 这样的输出就成功了。看到「不是内部或外部命令」或者 `command not found`，说明没装好，回去重装一遍。

## 第二步：告诉 Git 你是谁

Git 会在每次提交里记下「这是谁提交的」。所以先告诉它。

```
git config --global user.name "你的名字"
git config --global user.email "你的邮箱"
```

名字随便写，真名或者网名都行。邮箱填你以后要用来注册 GitHub 的那个。

`--global` 的意思是「这台电脑上所有项目都用这个设置」，配一次就行。

这两条命令敲完没有任何反应。**没有反应就是成功了。** 想确认一下，敲：

```
git config --list
```

会列出一堆配置，往下找，看到你刚填的名字和邮箱就对了。

## 第三步：建一个仓库

先建一个专门练习用的文件夹，别拿你重要的东西练：

```
mkdir ~/练手
cd ~/练手
mkdir 第一个仓库
cd 第一个仓库
```

`mkdir` 是建文件夹，`cd` 是走进去。敲完可以敲 `pwd` 看看自己在哪，应该显示类似 `/Users/你的名字/练手/第一个仓库`。

现在把这个文件夹变成 Git 仓库：

```
git init
git branch -m main
```

第一条会输出一句：

```
已初始化空的 Git 仓库于 /Users/zhangsan/练手/第一个仓库/.git/
```

（英文系统上会显示 `Initialized empty Git repository in ...`，同一个意思。）

这句话的意思是：Git 在这个文件夹里建了一个隐藏目录叫 `.git`。

你的全部历史都存在这个目录里。把它删掉，Git 的记录就全没了，文件夹会变回一个普通的文件夹。所以别去动它。

第二条是把主分支改名叫 `main`。Git 老版本默认叫 `master`，会提示一句「使用 master 作为初始分支的名称」。GitHub 现在默认用 `main`，改成一样，以后不容易混。

`git init` 一个文件夹做一次就够了，以后不用再敲。

## 第四步：第一次提交

现在文件夹是空的。建一个文件：

```
echo "# 我的第一个仓库" > README.md
```

这条命令的意思是：把引号里那句话写进一个叫 `README.md` 的文件。没有这个文件就新建，有就覆盖。

用编辑器打开看看（Git Bash 里可以敲 `notepad README.md`，Mac 上敲 `open README.md`），里面应该是 `# 我的第一个仓库`。

现在看 Git 怎么想：

```
git status
```

输出：

```
位于分支 main

尚无提交

未跟踪的文件:
  （使用 "git add <文件>..." 以包含要提交的内容）
	README.md

提交为空，但是存在尚未跟踪的文件（使用 "git add" 建立跟踪）
```

「未跟踪」是说你还没告诉 Git 要管这个文件。

这里有个关键的地方：**Git 不会自动接管文件夹里所有东西。** 因为很多文件不该被记录，比如临时文件、编译出来的产物、你自己不想传上去的东西。哪些要管，得你一个个说。

现在告诉它：

```
git add README.md
```

再敲一次 `git status`：

```
位于分支 main

尚无提交

要提交的变更：
  （使用 "git rm --cached <文件>..." 以取消暂存）
	新文件：   README.md
```

`README.md` 从「未跟踪的文件」挪到了「要提交的变更」下面。这就是「放进篮子了」。

存进历史：

```
git commit -m "加上 README"
```

`-m` 后面是这次提交的说明，一句话说清你干了什么。

敲完再 `git status`：

```
位于分支 main
无文件要提交，干净的工作区
```

「干净的工作区」意思是：你现在所有改动都提交过了，没有遗漏。

### 为什么中间要有「放进篮子」这一步

因为一次提交应该只做一件事。

假设你同时改了五个文件，其中三个是在修一个 bug，两个是在加一个新功能。如果一次全提交了，将来想「只把这个 bug 的修改撤掉」，你没办法，因为两件事混在一起了。

分开提交，历史才清楚。`git add` 就是让你有机会挑：这次只提交这三个文件。

这个「篮子」的正式叫法是**暂存区**。所以 Git 里其实有三块地方：你正在改的文件叫工作区，挑出来的改动叫暂存区，提交后的历史叫仓库。记住这三块，Git 的大部分命令你都能猜出是干什么的。

## 第五步：再提交两次

只提交一次感受不到 Git 的好处。再改两次：

```
echo "第一行" >> README.md
git add README.md
git commit -m "加第一行"
```

注意这里是 `>>`（两个大于号），意思是「追加到文件末尾」，不会覆盖原来的内容。

```
echo "第二行" >> README.md
git add README.md
git commit -m "加第二行"
```

现在你有了三次提交。

## 第六步：看历史

```
git log --oneline
```

输出：

```
ac27b8f (HEAD -> main) 加第二行
b581ee8 加第一行
1dfe8a0 加上 README
```

最近的在最上面。每行前面那串字符是提交的编号，后面是你写的说明。

括号里那个 `HEAD -> main` 的意思是「你现在站的位置是 main 分支的最新提交」。

不加 `--oneline` 能看到更多：

```
commit ac27b8fd6aefdc51b5cb728237cfd209d4871714
Author: 小张 <xiaozhang@example.com>
Date:   Mon Sep 14 17:51:12 2026 +0800

    加第二行
```

四十位的完整编号、作者、时间、说明，都在这里。

那个编号是拿这次提交的内容算出来的。内容变一个字，编号就完全不同。所以历史改不了：你一动，编号变了，后面所有提交都记着「我的上一条是谁」，整条链全对不上。

平时不用看全，`--oneline` 给的七位缩写够用了。

## 第七步：回到过去

找到第一次提交的编号（上面例子里是 `1dfe8a0`，你自己的会不一样），然后：

```
git checkout 1dfe8a0
```

打开 `README.md` 看一眼。它变回最早的样子了，只剩 `# 我的第一个仓库`，后面加的两行都不见了。

**这就是「回到过去」。** 你的文件真的回到了那一刻的状态。

这时候敲 `git status`，会看到：

```
头指针分离于 1dfe8a0
```

「头指针分离」听着吓人，其实意思是：你现在没站在任何分支上，而是直接站在某一次提交上。在这个状态下做的提交，如果不记下编号，回头就找不到了。

看够了就回来：

```
git checkout main
```

再打开 `README.md`，两行又回来了。

## 第八步：分支

分支是 Git 最有用的东西。

**分支就是一条独立的时间线。** 你从当前状态分出去一条，在这条线上改东西、提交，主线上的文件一点不动。做完了觉得可以，就合回主线；觉得不行，把这条线删掉，主线还是原样。

建一条，起名叫「试验」：

```
git checkout -b 试验
```

`-b` 的意思是「顺便建一个新的分支」。敲完 `git status`，第一行会变成 `位于分支 试验`，说明你已经在上面了。

改点东西，提交：

```
echo "试验分支上加的" >> README.md
git add README.md
git commit -m "试验分支的改动"
```

现在切回主线：

```
git checkout main
cat README.md
```

`cat` 是把文件内容打印到屏幕上。你会看到刚才加的那行**不见了**。它只存在于试验分支上，主线完全没受影响。

这就是分支的价值：你可以放心大胆地试，试坏了主线一点事没有。

觉得可以了，就合回来：

```
git merge 试验
```

输出：

```
更新 ac27b8f..8b32850
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)
```

再 `cat README.md`，那行回来了。

`Fast-forward` 是「快进」的意思。主线从分出去到现在没动过，所以 Git 只要把指针往前挪一下就行，不需要真的合并。这是最简单的一种情况。

分支用完了可以删掉：

```
git branch -d 试验
```

删分支只是删掉这个名字，上面提交的内容已经合进主线了，不会丢。

## 第九步：冲突

冲突听着吓人，其实就是「两条线上改了同一个地方，Git 不知道该听谁的」。

亲手做一次。开两条分支，改同一个文件：

```
git checkout -b 甲
echo "甲改的" > 内容.txt
git add 内容.txt
git commit -m "甲改的"

git checkout main
git checkout -b 乙
echo "乙改的" > 内容.txt
git add 内容.txt
git commit -m "乙改的"

git checkout main
git merge 甲
git merge 乙
```

最后一步会失败，输出：

```
自动合并 内容.txt
冲突（添加/添加）：合并冲突于 内容.txt
自动合并失败，修正冲突然后提交修正的结果。
```

打开 `内容.txt`，里面变成了这样：

```
<<<<<<< HEAD
甲改的
=======
乙改的
>>>>>>> 乙
```

读法是：`<<<<<<<` 到 `=======` 之间是当前分支上的内容，`=======` 到 `>>>>>>>` 之间是另一条线上的内容。

你要做的就是把整个文件改成你最终想要的样子，把那些尖括号和等号全删掉。

比如改成：

```
甲改的
乙改的
```

或者只留一句，看你想要什么。

改完之后：

```
git add 内容.txt
git commit -m "把两边的改动合到一起"
```

冲突就解决了。整个过程没有任何神秘的地方，Git 只是停下来问你一句：这里要哪个。

## 第十步：推到 GitHub

先在 GitHub 上注册账号，然后点右上角的加号，新建一个仓库（New repository）。

**不要勾选「Initialize with a README」**，因为你本地已经有东西了，勾了反而会冲突。仓库名随便起，其他都不用动，点创建。

创建完页面会给你一段命令，大概长这样：

```
git remote add origin https://github.com/你的用户名/仓库名.git
git branch -M main
git push -u origin main
```

第一行是告诉 Git「远程仓库在哪」。`origin` 是给这个远程地址起的代号，只是个名字，你叫它别的也行。

第二行是确认你的主分支叫 `main`。

第三行推上去。`-u` 是记住这个对应关系，以后直接敲 `git push` 就行，不用再写后面那一串。

推的时候会弹出登录。**GitHub 现在不收密码了**，要输「个人访问令牌」。这个东西在 GitHub 网页的设置里生成，生成后复制下来当密码用。步骤有点绕，遇到的时候搜「GitHub 个人访问令牌」，跟着做一遍。

推完刷新一下 GitHub 页面，你的文件就在上面了。地址栏那个链接可以直接发给同学。

### 别人先推了东西，你推不上去

如果远程有别人提交的、你本地没有的改动，`git push` 会被拒绝：

```
 ! [rejected]        main -> main (fetch first)
错误：无法推送一些引用到 'origin'
提示： 更新被拒绝，因为远程仓库包含您本地尚不存在的提交。
提示： 如果您希望先与远程变更合并，请在推送前执行 'git pull'。
```

按它说的先拉下来：

```
git pull --no-rebase
```

新版 Git 不加 `--no-rebase` 会报一句「需要指定如何调和偏离的分支」。这两个词的区别现在不用管，记住拉不下来就加它。

如果两边改的不是同一个地方，拉完直接 `git push` 就好了。如果冲突了，按第九步的办法处理：打开文件、改好、`git add`、`git commit`、再推。

## 第十一步：什么东西不该传上去

有些文件不该进仓库。名单写在项目根目录一个叫 `.gitignore` 的文件里，一行一个：

```
.env
*.log
node_modules/
```

`node_modules/` 末尾的斜杠表示这是个文件夹。`*` 是通配符，`*.log` 表示所有以 `.log` 结尾的文件。

这个文件建好之后，里面的名单在 `git status` 里就不会出现了。你可以自己验证一下：建一个 `.env`、一个 `app.log`、一个 `node_modules` 文件夹，敲 `git status`，会发现它们一个都没出现。

`.gitignore` 这个文件本身要提交进仓库，因为它是项目的一部分。

## 密钥提交上去了，删掉也没用

这是新手最容易吃大亏的地方。实际做一遍给你看。

```
echo "密钥=abc123" > .env
git add -f .env
git commit -m "不小心提交了密钥"
git rm --cached .env
git commit -m "把密钥删掉"
```

`-f` 是强制提交，因为 `.env` 在忽略名单里。`--cached` 是只从 Git 的记录里删掉，工作区的文件留着。

现在敲 `git log --oneline`，历史里已经看不到 `.env` 这个文件了。但是去搜一下历史里的内容：

```
git log -p --all | grep "abc123"
```

能搜到。**密钥还在历史里，任何拿到这个仓库的人都能翻出来。**

想彻底清掉，要重写整个历史，很麻烦，而且所有提交的编号都会变。所以省事的办法只有一个：

`git add` 之后敲一次 `git status`，看看篮子里有哪些文件。见到 `.env`、`config.json`、`id_rsa` 这种名字，停下来确认一下。

## 中文文件名显示成乱码

如果你提交了中文名字的文件，`git status` 里可能显示成这样：

```
	双方添加：   "\345\206\205\345\256\271.txt"
```

Git 默认把非英文字符转义了，看着难受。关掉它：

```
git config --global core.quotepath false
```

关掉之后同样的文件会正常显示成 `内容.txt`。

## 动手任务

一、装好 Git，配好名字和邮箱，用 `git config --list` 确认。

二、建一个仓库，完成三次提交，每次提交说明写清做了什么。写完敲 `git log --oneline` 看结果。

三、找到第一次提交的编号，`git checkout` 过去看一眼，再 `git checkout main` 回来。

四、开一条分支，改点东西提交，切回主线确认改动不在，再合并回来，然后删掉分支。

五、制造一次冲突并解决它。

六、建 `.gitignore`，写进去三个该忽略的东西，建出对应的文件，用 `git status` 验证它们确实没出现。

七、推到 GitHub。

## 正式产出

一个公开的 GitHub 仓库，要有：

- 一份 `README.md`，说清这个仓库是什么、怎么用
- 至少 5 次提交，提交说明都能看懂
- 一次分支和合并的记录
- 一份 `.gitignore`
- 里面没有任何密码、密钥、令牌

最后一条推之前自己翻一遍每个文件。做完把链接发给同学，他要是问你「这是干什么的」，说明 README 没写清楚。

## 卡住了看这里

**提示「不是内部或外部命令」或者 `command not found`。** Git 没装好，或者你用的不是 Git Bash。Windows 上装完之后一定要用 Git Bash，别用系统的命令提示符。

**提示要配置身份。** 那两条 `git config --global` 各敲一次。

**`git init` 敲错了地方。** 在不对的文件夹里建了仓库。删掉那个文件夹里的 `.git` 目录就行，用 `rm -rf .git`。

**GitHub 上头像不对。** 邮箱和账号不一致。用 GitHub 设置里的邮箱重新配一次。之前提交的不会自动改，不用管它。

**推不上去，说文件太大。** 把大文件加进 `.gitignore`，从篮子里移除。已经提交过要用专门的工具清理历史。

**提示「头指针分离」。** 敲 `git checkout main` 回来。

**合并时文件里多了一堆尖括号。** 冲突。手动改成你要的样子，`git add` 再 `git commit`。

**拉的时候说「需要指定如何调和偏离的分支」。** 敲 `git pull --no-rebase`。

**中文文件名是一堆数字。** 敲 `git config --global core.quotepath false`。

**提交说明写错了。** `git commit --amend` 可以改最近一次。已经推上去的别改，会让别人的历史对不上。

**想撤销，但怕丢东西。** 先敲 `git status` 和 `git log` 看清现在的状态。拿不准就先 `git stash` 把改动存起来，它是可逆的，随时能拿回来。

**合并搞乱了想放弃。** `git merge --abort` 会退回到合并之前的状态。

## 走完之后

Git 是唯一一个不管你走哪个方向都要用的工具，没有例外。

如果你提交时会认真写说明，看到别人的开源项目会去翻它的提交历史，说明你已经在用工程师的方式想问题了。不喜欢敲命令也没关系，重点是那个「随时能退」的感觉你摸到了。
