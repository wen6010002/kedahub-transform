## 你看不见的那一半

你打开一个购物网站，看到的是商品列表、价格、加入购物车按钮。这些是前端做的。

但商品信息不在你的浏览器里。价格是昨天刚改的，库存是实时扣减的，你加进购物车的东西明天换台电脑打开还在。

这些东西在你的浏览器外面，在一个你看不见的地方。那部分就是后端。

## 后端分五块

一个后端程序收到请求之后，做的事可以分成五块。不管多复杂的系统，拆开都是这五块。

### 第一块：接住请求

一个后端程序首先要能「听着」。它一直在等，看有没有人发请求过来。

收到请求之后，它先做几件检查：这个地址存不存在、这个人有没有登录、他有没有权限访问这个内容、他发过来的数据格式对不对。

这几步叫「入口处理」。大部分请求走到这里就结束了，要么是没登录，要么是参数写错了。

### 第二块：处理业务逻辑

通过检查之后，就进入正题了。

「用户下单」这个请求要做什么：检查库存够不够、算总价、扣库存、生成订单号、发一条通知。这些步骤叫业务逻辑，是后端最核心的部分。

**这一块也是最花时间的。** 难点在要考虑到各种意外：库存刚好在扣的时候被别人买走了怎么办、支付成功了但订单没生成怎么办、同一个请求因为网络问题发了两次怎么办。

新手写业务逻辑只管「正常情况」，老手一半的代码在处理「不正常情况」。

### 第三块：读写数据

业务逻辑要用到数据，数据在数据库里。

后端去数据库里查、改、存。这一步叫数据访问。

大部分系统的性能瓶颈就在这里。程序本身的逻辑跑得很快，慢的是数据库查询。一个没写好索引的查询能让整个页面卡住几秒。

### 第四块：调用别的服务

很少有系统是孤立的。

你要发短信，得调用短信服务商的接口。你要收款，得调用支付平台的接口。你要查快递，得调用物流公司的接口。你要用 AI，得调用模型的接口。

这些叫「第三方服务」。后端的工作是把它们串起来，处理好「对方挂了怎么办」「对方返回慢怎么办」。

### 第五块：返回结果

最后一步，把结果按约定的格式发回去。

前端拿到这个结果，再把它渲染成你看到的页面。

## 一个后端工程师一天在写什么

外面的人以为后端就是「写接口」。实际上写接口那部分代码可能只占一天的两成。

剩下八成在干这些：

**看日志。** 线上出了个 bug，用户说「我的订单不见了」。得去日志里翻，找到那次请求，看它经过了哪些步骤、在哪一步出错。

**改查询。** 有个页面加载要三秒，查出来是某条数据库语句没走索引。加上索引，变成两百毫秒。

**处理边界情况。** 用户把数量填成了负数、填成了汉字、填成了一个特别大的数。每种都要处理。

**写测试。** 保证改完这个功能之后，别的功能没被弄坏。

**跟别人对接。** 前端说「这个字段能不能加上」，产品说「这个逻辑要改一下」，运维说「你这个服务内存占用太高了」。后端是这些需求的落地方。

**上线和回滚。** 新版本发上去出问题了，得能快速退回来。

## 一个真实的场景

一个学生做了一个校园二手交易的小网站，自己测试的时候一切正常。

上线第二天，有同学反馈：「我点了两次提交，结果发布了两个一模一样的商品。」

他去看代码，发现逻辑是这样的：用户点提交 → 后端插入一条商品记录。

问题在于，网络不好的时候，浏览器可能把同一个请求发了两次。后端不知道这是重复的，就插了两条。

**这种情况叫「重复提交」，是所有后端都要处理的问题。**

解决办法是让每个提交请求带一个独一无二的编号。后端收到之后先看一眼这个编号有没有处理过，处理过就直接返回上次的结果，不再插一遍。

他改完之后，重复提交的问题没了。同时他也意识到一件事：**自己测试的时候网络很好，所以从来没触发过这个问题。**

**后端的大部分工作就是在想「什么情况下会出问题」，而不是「正常情况下能不能跑通」。**

## 它的边界

**后端管不了界面。** 它只返回数据，长什么样是前端的事。

**后端不是越复杂越好。** 一个只有几十个人用的小工具，用不着微服务、消息队列、分布式缓存。上来就堆这些，维护成本比收益大得多。

**后端语言之间差别没那么大。** Java、Python、Go、Node.js 都能做后端。选哪个更多看团队和生态，不看你个人偏好。学会一个，换另一个大概两三个月。

**后端做的事情用户看不见。** 做得好的时候没人夸，出问题的时候全是你的。这一点要有心理准备。

## 数据不对，先分哪一端
**遇到「数据不对」的问题，先分清是哪一端的问题。**

刷新页面之后数据是对的，说明是前端显示的问题。

刷新之后还是不对，说明是后端返回的数据就不对，或者数据库里存的就是错的。

**看后端到底返回了什么**，这是最有用的一招。按 F12，切到 Network 面板，点开任意一条请求，看 Response 那一栏。里面是后端原样返回的内容。前端显示的跟这个对不上，就是前端的问题。

**让 AI 帮你排查的时候，把 Response 的内容贴给它。** 只说「我的页面数据不对」，它只能猜。把后端实际返回的东西贴出来，它能立刻判断是哪边的问题。

**一个该养成的习惯**：任何会改变数据的操作（提交、删除、支付），都要防重复。这个坑每个人都会踩一次。

## 自己试一下

### 看一眼后端返回的原始数据

在浏览器地址栏里敲这一行，回车：

```
api.github.com/users/torvalds
```

（这是 GitHub 的一个公开接口，返回一个用户的信息。不用登录，谁都能看。）

屏幕上会出现一堆这样的东西：

```json
{
  "login": "torvalds",
  "id": 1024025,
  "name": "Linus Torvalds",
  "public_repos": 8,
  "followers": 230000
}
```

**这就是后端返回的东西。** 没有样式、没有排版、没有按钮，只有数据。

（如果打不开，换一个：`api.github.com/users/octocat`。还不行说明网络问题，跳过这一步也行。）

### 想想刚才发生了什么

你敲的是一个地址，拿回来的却是一段数据，不是网页。

这中间发生的事：你的浏览器发了一个请求出去，GitHub 的服务器收到之后，去它的数据库里查了这个人，把查到的信息整理成上面那种格式，返回给你。

**服务器返回数据，浏览器把它渲染成页面。这两件事是分开的。**

你平时看到的网页，是浏览器拿着这些数据（或者别的地方拿来的数据）画出来的。

### 换个角度看真实的请求

随便打开一个你常用的网站，按 F12，切到 Network 面板，刷新页面。

在那一堆请求里找找看有没有返回 JSON 的（点开一条，看 Response 里是不是花括号开头）。

找到的话，你就看到了这个网站的后端正在给你的浏览器发什么数据。

---

后端就是接住请求、处理逻辑、读写数据、调用别的服务、返回结果这五块。你在地址栏里看到的那个 JSON，就是它最终的产物。

## 几个常见的误解

**「后端就是写接口。」** 写接口大概只占两成时间。剩下八成在看日志、改慢查询、处理边界情况、写测试、跟别人对接。

**「本地能跑，线上就能跑。」** 环境不一样。本地是你自己的电脑，线上是另一台机器，系统版本、装的东西、网络环境都可能不同。所以部署是单独一门手艺，第 10 站专门讲。

**「后端慢就是服务器配置不够。」** 大部分时候是代码或数据库的问题。一条没走索引的查询能让页面卡三秒，换个再贵的服务器也一样卡。加配置是最后一步，不是第一步。

**「后端做的事情用户看不见，所以不重要。」** 这话说反了。用户看不见它，但它决定了数据对不对、会不会丢、能不能同时很多人用。出了问题，用户第一时间感受到。
