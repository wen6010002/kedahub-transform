# 接口 · 精通版

前后端初识 · 第 9 站

时间：1 个半小时到 2 小时。动手 80 分钟，留 30 分钟自己加接口。

做完你会有一个：一个自己写的小服务，开着三个接口，别人访问地址能拿到你定义的数据。

---

## 先把东西装上

这一站用 Node.js 写接口。如果你在第 4 站已经装过了，跳过这节。

打开终端（Windows 用 Git Bash，Mac 用系统自带终端），敲：

```
node --version
```

看到类似 `v22.22.2` 这样一行，就是装好了。

没装的话，看第 4 站精通版的第一步，那里有完整的安装步骤。

## 你有一个服务，但别人不知道能问它什么

第 4 站你写了个服务，能返回一些数据。但有个问题：**别人（包括你自己过几天回来看）不知道这个服务开了哪些「口子」。**

哪个地址能返回什么数据？要不要带参数？参数叫什么？这些问题没写清楚，这个服务就只有你自己能用，而且过两周你自己也忘了。

这一站做的，就是给服务开出几个**接口**，每个接口有明确的地址、明确的用途、明确返回什么。做完之后，任何人都能照着你的说明去调用。

---

## 接口的三要素

一个接口，由三样东西说清楚：

**地址。** 比如 `/api/students`，意思是「所有学生的列表」。

**返回什么。** 访问这个地址，返回一段 JSON，里面是学生列表。

**怎么用。** 是直接访问，还是要带参数。

这三个东西合起来，就是一个接口的「说明书」。别人不用看你的代码，只看说明书，就知道怎么用。

---

## 第一次动手：一个返回列表的接口

新建一个文件夹：

```
mkdir 接口练习
cd 接口练习
```

新建一个文件叫 `server.js`，敲进这些内容：

```js
var http = require('http');

var students = [
  { id: 1, name: '张三', score: 82 },
  { id: 2, name: '李四', score: 91 },
  { id: 3, name: '王五', score: 67 }
];

var server = http.createServer(function (req, res) {
  if (req.url === '/api/students') {
    res.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
    res.end(JSON.stringify(students));
    return;
  }

  res.writeHead(404, { 'Content-Type': 'application/json; charset=utf-8' });
  res.end(JSON.stringify({ error: '没有这个接口' }));
});

server.listen(3000, function () {
  console.log('服务起来了');
});
```

存盘，终端里敲：

```
node server.js
```

打开浏览器，访问：

```
http://localhost:3000/api/students
```

你会看到：

```json
[{"id":1,"name":"张三","score":82},{"id":2,"name":"李四","score":91},{"id":3,"name":"王五","score":67}]
```

**这就是你的第一个接口。** 地址是 `/api/students`，返回所有学生的 JSON。

注意到这里有个约定：接口的地址都用 `/api/` 开头。这只是习惯，不是规定，表示「这是给程序取数据用的，不是给人看的网页」。你自己写也建议这么写。

## 第二层：一个能按 id 查单个的接口

列表接口返回所有人，但有时你只想查一个人。加一个接口，通过参数指定查谁。

在文件最上面，`var http = require('http');` 下面加一行：

```js
var url = require('url');
```

`url` 是 Node 自带的一个模块，用来解析地址里的参数。

然后在 `if (req.url === '/api/students')` 这段下面，加上：

```js
  if (req.url.indexOf('/api/student?id=') === 0) {
    var id = Number(req.url.split('=')[1]);
    var found = students.filter(function (s) { return s.id === id; });
    res.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
    res.end(JSON.stringify(found.length ? found[0] : { error: '没找到' }));
    return;
  }
```

存盘，回终端按 Ctrl 加 C 停掉旧服务，再 `node server.js` 重跑。

浏览器访问：

```
http://localhost:3000/api/student?id=2
```

你会看到：

```json
{"id":2,"name":"李四","score":91}
```

**地址里的 `?id=2` 就是参数**，意思是「我要 id 是 2 的那个人」。`req.url` 拿到的是完整地址，我们用 `split('=')` 把它从等号处切开，取后面的数字。

再试试查一个不存在的人：

```
http://localhost:3000/api/student?id=99
```

你会看到：

```json
{"error":"没找到"}
```

**这就是接口要处理的事：用户可能传一个不存在的东西，你不能崩，要返回一个「没找到」的说明。** 真实的接口，一半的代码在处理这种「情况不对怎么办」。

## 第三层：用一个工具来测接口

浏览器只能发 GET 请求，而且看起来不够直接。做后端的人测接口，用命令行工具 `curl`。

它第 6 站已经出现过。现在用来测你自己的接口。服务保持开着，另开一个终端窗口，敲：

```
curl http://localhost:3000/api/students
```

返回：

```json
[{"id":1,"name":"张三","score":82},{"id":2,"name":"李四","score":91},{"id":3,"name":"王五","score":67}]
```

加个 `-i`，看完整的信息，包括状态码：

```
curl -i http://localhost:3000/api/student?id=2
```

你会看到：

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"id":2,"name":"李四","score":91}
```

**第一行的 `200` 是状态码，第二行是响应头，空一行之后是数据。** 以后你跟别人说「这个接口返回 200」，意思就是「它正常工作」。

再测一个不存在的接口：

```
curl -i http://localhost:3000/abc
```

你会看到 `HTTP/1.1 404 Not Found`，然后是一段 `{"error":"没有这个接口"}`。

**`curl` 是后端日常**：起服务之后，用它快速验证每个接口对不对。比每次都开浏览器快得多。

## 第四层：写一份接口说明

接口写完，还差最后一件最重要的事：**写清楚每个接口是干什么的。**

别人（和以后的你）要知道：有哪些接口、怎么调、返回什么。写成一个文本，放在项目里，比如 `README.md`：

```
## 接口说明

### 学生列表
地址：GET /api/students
返回：所有学生的数组

### 单个学生
地址：GET /api/student?id=编号
返回：那一个学生，找不到返回 {"error":"没找到"}
```

**这一份说明，价值不亚于代码。** 没有它，这个服务就是一堆别人看不懂的地址。有了它，谁都能上手。

真实的公司里，接口文档比这复杂得多，有专门的格式和工具，但核心就这三点：地址、参数、返回什么。

## 动手任务

一、照上面的代码，把两个接口跑起来，用浏览器和 curl 各访问一遍。

二、加一个「按分数查」的接口 `/api/pass`，返回所有 score 大于等于 60 的学生。提示：用 `filter`。

三、给 `server.js` 加一个 `/api/info` 接口，返回一个对象，里面有你的名字、学校、以及「现在服务器的时间」。

四、给每个接口都写上说明，写进一个 `README.md` 文件。

五、故意把 `JSON.stringify(students)` 写成 `JSON.stringify(student)`（少个 s），看接口返回什么。屏幕上的报错信息会告诉你是哪里错了，改回来。

## 正式产出

一个开着至少三个接口的服务，外加一份接口说明。

要求：

- 至少三个接口：一个列表、一个按参数查单个、一个你自己设计的
- 每个接口返回正确的 JSON
- 访问不存在的地址返回 404 和一段错误 JSON，而不是崩掉
- 有一份 `README.md`，写清了每个接口的地址、参数、返回什么
- 你能用 curl 分别测通三个接口，说出它们返回的状态码

## 卡住了看这里

**提示 `Error: listen EADDRINUSE`。** 3000 端口被占着，多半是上一个服务没停。回到跑服务那个终端按 Ctrl 加 C，或者把端口改成 3001。

**改了代码，浏览器还是旧结果。** Node 不会自动重载。改完要 Ctrl 加 C 停掉，再 `node server.js` 重跑。

**访问 `/api/student?id=2` 返回的是全部学生。** 你那个按 id 查的 `if` 可能写在了列表 `if` 后面，列表的判断先把请求接走了。把按 id 查的判断放在列表判断前面。

**返回的 JSON 里中文变乱码。** `Content-Type` 里少了 `charset=utf-8`。中文数据必须带这个。

**`split('=')` 之后取到的 id 是 `NaN`。** 你访问的地址里 `?` 后面没有 `id=`，或者 `id=` 后面是空的。检查地址拼写。

## 走完之后

你现在会写接口了。接口是后端最核心的东西，一个后端的工作，大部分时间就是在写接口、改接口、看接口返回。

判断自己对不对路子，看一个感觉：当你用 curl 敲一下地址，屏幕上跳出自己定义的那段 JSON，你有没有觉得「数据被我管得明明白白」。

如果你觉得「给数据开一个规规矩矩的入口，让别人照约定来取」，这件事有意思，后端这条线适合你。

## 想再往下看

真实的项目不会用 `http` 模块手写，会用框架。搜「Express 路由」，你会发现它把上面那些 `if` 换成了更清楚的写法，但接口三要素没变。

想知道「接口之间的约定」发展出了什么规范，搜「RESTful API 设计」，看看大家约定俗成的地址命名规则。
