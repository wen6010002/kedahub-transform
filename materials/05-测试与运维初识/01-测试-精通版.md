测试与运维初识 · 第 1 站

做完你会有一个：一套能跑的测试，能抓住「改坏的代码」。

## 你写了个函数，怎么保证它一直对

假设你写了个函数：判断一个数字是不是偶数。

现在它是对的。但你过几天要改它，改成「判断能不能被 3 整除」。你怎么保证，改的时候没把它改坏？

靠眼睛看？改一个地方，可能影响三个地方，眼睛看不过来。

正解是：**写一组测试，把你「认为它该怎么样」记下来。以后每次改，跑一遍测试，测试告诉你改坏没有。**

这一站，你亲手给一个函数写测试。

---

## 测试的本质：断言

先搞懂测试里最核心的一个动作，叫**断言**。

断言，就是「我断言，这个结果应该等于那个」。比如：

「我断言，`isEven(2)` 的结果，应该等于 `true`。」

机器跑一下 `isEven(2)`，看是不是 `true`。是，这条断言通过；不是，这条断言失败。

**测试，就是一堆这样的断言。** 你把「什么算对」写成一条条断言，让机器逐条验证。这跟你手工「点一下看看」的区别是：机器不会烦、不会漏，几秒钟能跑几百条。

## 第一次动手：写函数，写测试

新建一个文件夹，建两个文件。

第一个文件叫 `math.js`，放你被测的函数：

```js
function isEven(n) {
  return n % 2 === 0;
}

module.exports = { isEven: isEven };
```

`n % 2` 是「n 除以 2 的余数」，余数是 0 就是偶数。最后一行 `module.exports` 是「把这个函数分享出去」，让测试文件能用它。

第二个文件叫 `test.js`，放测试：

```js
var { isEven } = require('./math.js');

var pass = 0;
var fail = 0;

function check(name, got, want) {
  if (got === want) {
    pass = pass + 1;
    console.log('通过：' + name);
  } else {
    fail = fail + 1;
    console.log('失败：' + name + '（期望 ' + want + '，实际 ' + got + '）');
  }
}

check('2 是偶数', isEven(2), true);
check('3 不是偶数', isEven(3), false);
check('0 是偶数', isEven(0), true);
check('负数 -4 是偶数', isEven(-4), true);

console.log('共 ' + (pass + fail) + ' 个测试，通过 ' + pass + ' 个，失败 ' + fail + ' 个');
```

存盘，终端里进到文件夹，敲：

```
node test.js
```

你会看到：

```
通过：2 是偶数
通过：3 不是偶数
通过：0 是偶数
通过：负数 -4 是偶数
共 4 个测试，通过 4 个，失败 0 个
```

**你刚写了人生第一套测试。** 拆开看：

`check` 函数是「一条断言的执行器」：拿到「名字、实际结果、期望结果」，比较，然后打通过或失败。

下面四行 `check(...)`，就是四条断言。每一条，都是「什么算对」的一条记录。

## 第二层：看看测试怎么「抓 bug」

现在干一件关键的事：**故意把代码改坏，看测试能不能抓住。**

打开 `math.js`，把 `n % 2 === 0` 里的 `0` 改成 `1`：

```js
function isEven(n) {
  return n % 2 === 1;
}
```

（改成 `=== 1`，这个函数就变成「判断奇数」了，跟名字「isEven 是偶数」完全相反，这是故意改坏的。）

存盘，再跑：

```
node test.js
```

你会看到：

```
失败：2 是偶数（期望 true，实际 false）
通过：3 不是偶数
失败：0 是偶数（期望 true，实际 false）
通过：负数 -4 是偶数
共 4 个测试，通过 2 个，失败 2 个
```

**看到没有？测试当场抓住了你的 bug。** 它精确地告诉你：哪几条错了、期望什么、实际拿到了什么。

**这就是测试最值钱的地方。** 你以后每次改代码，跑一遍测试，如果全绿（全通过），说明没改坏；如果有红的（失败），说明你刚改的地方出问题了，而且它还告诉你是哪里。

把 `math.js` 改回 `=== 0`，跑一遍确认回到全绿。

## 第三层：给你的测试「加料」

刚才那四条测试，只测了「偶数、奇数、0、负数」。真实情况比这复杂，往里加。

### 加边界情况

0 算不算偶数？负数呢？这些「边界」最容易出 bug，要多测。加上：

```js
check('很大的偶数', isEven(1000000), true);
check('负奇数', isEven(-7), false);
```

### 加「刁难」的输入

有人可能传个不是数字的东西进去，比如文字：

```js
check('传文字会怎样', isEven('不是数字'), false);
```

（注意：`'不是数字' % 2` 的结果是 `NaN`，`NaN === 0` 是 `false`，所以返回 `false`。这条测试能过，但你顺手测了「奇怪输入会不会崩」。）

**加测试的原则就一条：把「可能出问题的输入」都列上。** 边界、奇怪输入、极端值，都是 bug 高发区。

## 动手任务

一、照上面的代码，把函数和测试跑起来，看到全绿。

二、故意改坏 `math.js`（比如把 `% 2` 改成 `% 3`），跑测试，看它怎么报失败。再改回来。

三、给你的函数加五条新测试：一个很大的数、一个负数、一个 0、一个「刁难」的输入。

四、自己写一个新函数（比如「判断一个数是不是正数」`isPositive`），再给它写四条测试，跑通。

五、故意给新函数留个 bug（比如正数判断写成了 `>= 0`，把 0 也算成「正数」），看测试能不能抓住。

## 正式产出

**一套能跑的测试，包含你写的两个函数和它们的测试。**

要求：

- 至少两个函数（isEven 和 isPositive 或别的）
- 每个函数至少四条测试，包含边界情况
- 你演示过「改坏代码，测试能抓住」，再改回来
- 你能说清 `check` 函数里那三行在干嘛

## 卡住了看这里

**提示 `Cannot find module './math.js'`。** 两个文件没在同一个文件夹里，或者文件名对不上。`ls` 看一眼当前目录，确认 `math.js` 和 `test.js` 在一起。

**提示 `SyntaxError`。** 多半是中英文符号混了。检查 `{ }`、`( )`、`'` 都要英文的。

**测试全红，全显示「失败」。** 可能是 `math.js` 里 `module.exports` 那行漏了，或者函数名对不上。检查 `require('./math.js')` 里拿到的名字，和 `math.js` 导出的名字是不是一样。

**「失败」里出现 `NaN`。** 你传了不是数字的东西进去，`% 2` 算出来是 `NaN`（Not a Number）。这本身不算 bug，但你要知道「奇怪输入」会得到这种结果。

## 走完之后

你现在会写测试了。这件事的收益是长期的：**有了测试，你才敢放心改代码。**

没测试的人，改一处代码，是「赌它没改坏别处」。有测试的人，改完跑一遍，全绿就安心，红了就知道哪错了。

判断自己对不对路子，看一个感觉：当你故意改坏代码、看到测试「啪」地报出失败的那一刻，有没有一种「有张网兜着我」的踏实感。有的话，你会喜欢「写测试」这种「先把标准立起来」的活。

## 想再往下看

真实的项目不用手写 `check`，用现成的测试框架。Node 自带的叫 `node:test`，前端常用的是 Jest。搜「Jest 入门」，你刚才写的断言，到了框架里就是 `expect(x).toBe(y)`，本质一样。

想了解「测试」在团队里是怎么组织的、单元测试和集成测试怎么分工，回头翻第 1 站的探索版。
